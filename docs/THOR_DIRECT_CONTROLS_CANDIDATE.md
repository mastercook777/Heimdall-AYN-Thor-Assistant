# Thor Direct controller candidate (2026-10-14)

## Decision and scope

The owner asked to try a one-tap alternative to Shizuku setup on Thor. The preceding read-only feasibility probe is recorded in `THOR_PSERVER_FEASIBILITY.md`. This candidate uses the stock `PServerBinder` only to launch Heimdall's own constrained helper from the installed Debug APK. It exposes a new, opt-in **Thor Direct · Experimental** connection row. The first step covered physical-controller macro recording and replay. The next candidate adds Right Stick and Precision Aim through one shared native axis-output route. Mapped touch, touch macros, and the other Advanced Controls retain their established routes. Shizuku remains available if Thor Direct is disabled or unavailable.

The registered `codex/alpha-next@b2d978b` line has the same Java/C++ source as published `v0.4.0-alpha.1`; the public tag adds release metadata, docs, and wording. This candidate carries the published English/Chinese string changes to avoid reverting accepted copy. The Debug registry still labels the separate `.debug` package `0.2.0-alpha.1-debug`; this is a registry/versioning follow-up, not a claim that the published 0.4.0 APK was modified.

The app never accepts a shell command, event-node path, or helper socket name from a Profile, imported data, or UI input. Its fixed launch command validates the installed APK path as a shell atom and stays below Thor's observed PServer command-length boundary. The helper requires root UID, Android 13+, and `AYN Thor`, binds an abstract Unix socket named with a random 128-bit app-private nonce, and rejects peers other than the calling app UID. The socket protocol allows only ping, bounded controller capture, bounded controller replay, normalized right-stick output, and stop. It resolves the physical controller anew by the existing name/capability logic rather than a fixed event number. Ping checks JNI loading and actually opens the resolved node for zero-byte read and write before showing Ready.

The opt-in setting persists across app restarts. A fresh app process stops any prior helper at its socket before starting code from the currently installed APK. Turning the switch off sends Stop. A failed or interrupted helper marks the route unavailable; the existing Shizuku path can be used instead. The helper itself may remain blocked in `accept()` while Thor Direct is enabled and the app is not visible; this is a lifecycle item to evaluate on device before expanding its scope.

## Evidence and limitations

- The feasibility probe proved app-process access to stock PServer and preliminary root input access on one Thor firmware. It did not exercise this helper or write an event.
- On 2026-10-15, temporary instrumentation on the same Thor showed that 211-character no-op PServer commands returned normally while 311/411/511-character commands returned empty output. The first 469-character helper launch failed closed. The shorter APK-classpath launch then returned `READY`; logcat confirmed a root `app_process` helper for app UID 10253. This proves startup, the app-UID socket connection, JNI load, physical-controller resolution, and zero-byte read/write opens on this firmware. No input event was emitted in that startup probe.
- The follow-up smoke run returned `NO_EVENTS` from a 300 ms controller capture and `evdev sequence ok events=1` from a replay containing only `EV_SYN` (type 0, code 0, value 0). No button or stick state was sent. The opt-in setting persisted as `false` after test cleanup, and the root helper process exited. The temporary instrumentation runner was then removed and the normal runner restored.
- The Debug candidate compiles and is source/APK verified separately. The device probe proves helper startup and read/write access, but does not prove physical button recording, event replay, all-up cleanup, controller-mode switching, or user-visible UI behavior.
- The bridge is firmware-specific and experimental. A missing, denied, or changed PServer must leave the route unavailable, with no claim that all Advanced Controls work without Shizuku.
- No third-party Megingiard implementation code is included.

Precision Aim uses its separate Shizuku call site. A right-stick candidate therefore needs a per-capability readiness path and a route fixed for the whole gesture; switching between privileged routes while a nonzero axis is active could leave stale output.

The root helper serves one socket request at a time, and the replay path can continue after its caller disconnects. The JNI sequence emitter attempts recovery on write failure, but a process killed after a key-down event cannot run that cleanup. Continuous right-stick output is more sensitive. The new shared route fixes Thor Direct/Shizuku/app-direct selection for each gesture, validates normalized axis values in the helper, resolves native/Xbox controller axes there, and sends explicit neutral on UP/CANCEL/view detach/Activity recenter/Stop. The Right Stick gesture renews its nonzero output every 200 ms; the helper's independent watchdog attempts neutral after a 700 ms lease expires, with bounded retries on write failure. Precision Aim retains its existing short pulse and neutral timer. A killed helper cannot itself issue a neutral, and repeated device write failure cannot guarantee neutral; these remain device acceptance scenarios. Mapped touch remains on its existing route.

Cross-device direction: Megingiard's current README describes Thor `PServerBinder` startup and a wireless-ADB shell-daemon route elsewhere. Shizuku's official setup guide likewise uses Android wireless debugging on Android 11+ and requires restart after reboot. Heimdall currently consumes an authorized Shizuku UserService instead of owning pairing, daemon deployment, and wireless-ADB credentials. Preserve that general route while Thor Direct is expanded. Reconsider an in-app wireless-ADB bootstrap only after a specific second dual-screen device shows that guided Shizuku setup remains the primary barrier; do not import Megingiard's proprietary source-available implementation. References: https://github.com/stormpanda/megingiard#megingiard-system-service and https://shizuku.rikka.app/guide/setup/.
